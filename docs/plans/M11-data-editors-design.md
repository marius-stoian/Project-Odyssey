## 3. The schema subset and validator (US-190)
A schema is a JSON file with one of these keys on any node: `type` (`object`, `array`, `string`, `number`, `integer`, `boolean`), `properties` (named fields), `additionalProperties` (a schema for every other key: a map keyed by id), `items`, `required` (list of keys), `minimum`, `maximum`, `minItems`, `maxItems`, `maxLength`, `enum`, `default`, `description` (help text: what it is for), `example`, `ref` (`"catalog:items"`: the value must be a name in that catalog, and the form shows a picker), `format` (`rule` for a rule-language expression, `effect` for an effect line, `colour`, `frame` for an atlas frame, `time`), and at the root `title`, `provides` and `dataFile`.

- `provides`: `{ "catalog": "items", "at": "items[].id" }` says which values of the file make up a catalog; one file may provide several. Catalogs: weapons, plants, animals, effects, weather, characters, objects, items, recipes, professions, interactions, npc-classes, lights, building-kinds, pieces, levels, dialogues, quests, tiles, materials, needs, partner-types, tags (the union of every `tags` list, from the schema field `"ref": "tag"` hints) and any provided by a new schema (so a new file type needs only a schema).
- `index.json` maps globs under `assets/data/` to a schema file: `{ "weapons.json": "weapons", "interactions/*.json": "interaction", ... }`. A data file with no schema is a CI failure ("Coverage"); a `.dlg` file is text, checked by the dialogue parser, listed in the index with `"text"`.
- `unknown fields`: a key the schema does not name is a warning at load ("maybe a typo") and an error in CI and in the Editor, except keys named `note`, `comment` or starting with `_` or `//` (note fields).
- **Errors** read `assets/data/<file>:<line>: <field path>: <problem>` and name the allowed range: `weapons.json:23: weapons[2].damage: must be between 1 and 999 (is 0)`. The line comes from a small scanner that maps every JSON path to its line (`schema.cpp`, `JsonLines`), comments allowed.
- **Where it runs.** `readJsonFile` and the parse sites of the loaders call `sim::schema::checkLoaded(file, json)`; a `SchemaSet` is installed once by the game and the headless run from `assets/data/schemas/`. With none installed (a unit test reading a temporary file) nothing is checked. A type, range, enum or required error is a `DataError` (fatal for that file, as the loaders' own checks are today); unknown fields and dangling refs are warnings. Bad data never crashes the game (ARC-08).
- **Drift test.** `index.json` also names, per schema, the loader source files. The CI test collects the quoted keys each loader reads (`value("x")`, `at("x")`, `contains("x")`, `["x"]`, the `requireInt` field names) and fails by name when a loader reads a key its schema does not describe or a schema property is read by nobody (a list `readBy` in the index allows a field read by a helper in another file). It also loads every shipped file through the validator.

## 4. Help from schemas (US-190, US-191)
One help source (K-M11 step 1): each schema field's `description` and `example` become an entry of `EditorHelp` with the id `data.<schema>.<path>` (array indexes dropped: `data.weapons.damage`); `range` is made from `minimum`/`maximum` or `enum`. The Data tab's fields are given their help by `EditorHelp::apply` like every field of M10b, so the M10b coverage test covers them; a test fails by name for a schema field without a description.

## 5. Canonical writer and the Data tab (US-191)
- **Writer (changed at US-191, D-60 Q5).** A canonical writer would reformat a file the first time it is saved (the weapons are one object to a line with no space after the colon, the sim files have spaces, some files carry comments) and would lose every comment inside a file. Instead the open file is held as `nlohmann::ordered_json` and **saved by patching the text it was read from** (`src/sim/json_patch.*`): a small parser maps where every value stands; a changed value is replaced where it stands, a list or object that gained or lost entries is rebuilt in the style found in the original (one line or one entry to a line, the indentation, the space after colons and commas, new list entries kept on one line when their neighbours are), and everything else is copied byte for byte, comments and `note` fields included. With nothing changed the result is the file. Tests over the whole corpus: no change gives back every file byte for byte; every number, string and flag edited, every list grown and shrunk, every object given and robbed of a member: the patched text parses back to the edited document. A document with no text to patch (a new file) is written in the house style by `writeJsonText`. No one-time reformat of the shipped files is needed.
- **Tab.** A `Data` button of the Editor opens `DataEditor` over the map (like Events). Left: the file list (grouped by folder, search box), then the entry list of the file (one-per-entry files: the entry is the file; catalogs: the array element or object key; search). Right: the form. Esc comes back, Ctrl+S writes the file (temp file, rename, 3 backups as for every save), Ctrl+Z / Ctrl+Y walk the undo stack of the open file (snapshots of the document after each edit, up to 200; opening another file starts a new stack; closing with unsaved edits asks like the Level editor).
- **Form widgets** (all from `data_form.cpp`, reading the schema node): `integer` is a `NumberField` clamped to `minimum`..`maximum`; `number` is a `TextField` that accepts a decimal within its range; `string` is a `TextField` (a `ref` or `enum` makes it offer its `SuggestList` and the picker button; a `format: colour` field also draws a swatch); `boolean` is a `Toggle`; `object` is a group with a heading (open or closed by a click); `array` of scalars is one `TextField` with comma list (`listItems`), `array` of objects is a list of rows with Add, Remove, Up and Down; a map (`additionalProperties`) is a list of keyed groups with Add and Remove. A field with a mistake is outlined red with the validator's text under it. The form scrolls with the wheel and with Page Up and Down (the panel shows the visible rows only; it is rebuilt on scroll).
- **Reload.** A save calls `DataReload::changed(file)` and the file's set is read again (US-303). The set `next-start` disappears: see section 7.

## 6. References, rename and delete (US-193)
The reference index is built from the schemas' `ref` and `provides`: every value of a `ref` field is one use of one catalog entry; the index lists uses as `(file, line, path)`. Besides the data files it reads three more places with fixed rules: levels (`assets/levels/*.json`: placed kinds, weapons, effects, lights, the level's `rules`), `.dlg` dialogue files (only lines that hold a rule-language condition or effect: the words `if`, `when`, `do`, `give`, `take`, `quest`, `flag`, `has(`), and rule-language strings (`format: rule` / `effect` fields: whole identifiers only, so `berries` in `has(berries, 2)` is a use, "berries" in prose is not). Rename rewrites every use in one step (all files written, or none), lists each changed file and line, and is one undo step of the Data tab; Delete lists the uses and waits for a second click on Confirm. Entity actions (Create, Copy, Rename, Delete) work on any catalog that a schema `provides`, so a new catalog needs no code. Tags, states and the kind's interactions are ordinary fields; the interaction field opens the M9 graph editor at that interaction.

## 7. Live catalogs (CI-007, CI-021) (US-191)
Every holder of a catalog definition keeps the kind's id and looks the definition up each time it needs it: `WorldPlant::def` is replaced by lookups through `catalogs_.plant(kind)` (already done for plants by US-303), `ArcShot::weapon` and `Projectile::weapon` become weapon names, `starters_` becomes names, `heldWeapon()` looks up the hotbar's name, enemies keep `kind`. Lookups use a map built when the catalog is loaded, so a lookup is not slower than today's pointer plus compare. Then weapons, animals, effects and weather join the `catalog` set (reloaded together, all or nothing); `tiles.json` and `materials.json` stay at the next start because the map's cells hold tile numbers: their change is reported, never half-applied, and the form says so (the exit criterion only names entities, mechanics, story tuning, game rules and routines). **Built at US-191:** weapons, animals, effects and weather (the holders found: shots in the air, the starter weapons, the weather cycle; the hotbar, the lights and the effects already held names). **Left to US-194:** mechanics files (`sim/*.json`, `hero/*.json`) become the set `mechanics`: the loaders return plain data structs, the `World` and the hero life hold their data by value in one place each, and a reload swaps the struct between ticks (at the start of a tick, never inside one). A swap that would change an in-flight value in a way the model cannot take (the calendar's ticks per day, the size of the region) is refused with the reason, and the old data stays.

## 8. Mechanics, story tuning and the Quick check (US-194)
Every mechanics and story file has a schema, so it opens as a form with no extra code (US-190 + US-191). The **Quick check** button of the Data tab runs the clan simulation for 20 years on the current seed with the edited data in the same process, time-sliced: 30 simulated days a tick, so the screen stays alive and no thread is needed (ADR-007). The result is a summary: population at the end, births, deaths by cause (starvation, cold, age, wound, sickness, childbirth, feud), episodes started, and the previous run's numbers beside it (the previous run is the last check of this session, kept in memory only). Two runs with the same data and seed produce the same summary (the sim is deterministic, ADR-011). It reuses `sim::TestPlay`/`World` as `odysseus_headless` does; the headless program and the Editor share one function `runQuickCheck(dataDir, seed, years)` in `src/sim/quick_check.{h,cpp}`.

## 9. Game Rules (US-195)
`assets/data/rules/standard.json` with sections `newGame` (presets and comforts moved from `hero/hero.json`), `victory` (the thresholds that are in `hero.json` `dominion` and in code), `comfort`, and `systems: { weather, combat, rivals, tutorial, markers, chronicle, politics }` (each true/false, default true; `politics` is read by M13). `sim::PlayRules` loads a rules file (default `standard.json`), keeps it by value in the `World` and the game, and is passed to each system that has a switch (the switch is read once when a game starts, never per frame; the Editor's Play here and F5 read it again). The New Game screen gets a picker of the files in `assets/data/rules/`; a level may carry `"rules": "<name>"` (level format version bump with a migration; absent means the player's pick, then `standard`). The Game Rules page is the Data tab opened on that folder with a heading and a one-line summary of the switches; `hero.json` loses the moved keys (migration: the loader reads the old keys when the rules file lacks them, with a warning, for one version).

## 10. Routines (US-196)
A routine is the US-290 schedule format given to a role. Where schedules live: NPC classes (`npc-classes/<id>.json` `day`/`night`), kinds and NPCs. This story adds the **profession** as a role: `hero/professions.json` entries gain optional `day` and `night` in the same format, and `assets/data/sim/schedule.json` keeps the shared defaults. A block gains optional `prefer`: `{ tag: weight }` (weights as whole percent, 100 = neutral, 0 to 500). The M7 utility scoring multiplies an interaction's score by the active block's weight for each tag the interaction carries (the product of the matching weights, clamped); a need below its danger level still wins first (the US-290 interruption rule is applied before scoring). Clan members take their profession's routine when they have none of their own. The timeline view draws the 24 hours of the open schedule as a bar with a coloured block per entry; dragging a block's edge changes its start, the form below shows the same numbers, both edit the same schedule object, so there is one writer and one format. No `routines.json`, no second scheduler.

## 11. Picture pickers and cutting (US-192, Should)
The form widget for `format: frame` shows the frames of the atlas as a grid of pictures (the atlas is in memory); effect and animation fields show a preview that plays in the form. The Cut tool opens a sheet of `assets/sprites/`, the owner drags a rectangle and names it, and the cut is added to `cuts.json` and the atlas is rebuilt by the existing `odysseus_atlas` code (as a library call if one exists, otherwise by running the tool once; decided at the story, Q12).

## 13. Risks
| Risk | Mitigation |
|---|---|
| A schema is wrong and a shipped file stops loading | The CI test loads every shipped file; the validator is lenient on unknown fields at load |
| Reformatting 185 files in US-191 hides real diffs | The canonical writer is applied only to files the owner saves, plus one reviewed reformat commit of the files that differ, listed in the evidence |
| Swapping mechanics data in a live World corrupts a run | Swap only at a tick boundary; refuse changes the model cannot take; test: hash of a run with a swap equals hash with the new data from the start for fields that are read each tick |
| The rename touches the wrong text | Whole identifiers only, rule-language fields and directive lines only, a full list shown, one undo step |
| The tab is too big for one story | US-191 delivers the form, save, undo and live reload; entity actions are US-193 |
