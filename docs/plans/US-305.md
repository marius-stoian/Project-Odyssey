# US-305 Level edits win over the run save: plan and checks

Design: docs/plans/M10b-editor-help-design.md. Decisions: D-58 (live data, level edits win over the run save). Traces to EDT-11, ADR-010.

## How a run and a level relate (checked first)
- A hand-made level is a file in `assets/levels/`. A run on it is the clan, the hero, the plants' states, the timers, the placed people and the buildings, written by the autosave into the save folder (`clan.json`, `hero.json`, `things.json`, `buildings.json`, `npcs.json`, `trade.json`, `npc-life.json`). Nothing in the save holds a copy of the level: `loadAutosave` runs on a game that has already read the level file, and puts the saved state on top of it by id.
- `region.json` is the run's copy of a generated region (a seed), not of a level file. The level of a generated region is made from that seed (`levelFromRegion`), the Editor cannot open it, and there is no level file to edit. So the baseline is for hand-made levels only: a region run writes none and loads as before.
- What is stateless in a run (effects, lights, pickups, enemies and animals) is made from the level every time the game starts or plays; only plants (state and waiting timers), people, trade, and buildings carry run state that can disagree with an edited level.

## Built
- `src/game/level_baseline.*`: `LevelBaseline::of(level)` holds an id and an FNV-1a hash for every placed thing of six kinds (characters, pickups, plants, effects, lights, buildings); the hash is of the entry as the level file writes it (`entryText`, shared with `saveLevel` through `entryJson` in `level.cpp`, so a new field is counted the day it is written). `compareBaseline(baseline, level)` returns `LevelChanges`: per kind the ids that are new or changed (`updated`) and the ids that are gone (`removed`). `levelChangesMessage` makes the status line text ("The level updated 3 things").
- `things.json` version 3 adds `baseline`. Version 1 and 2 saves have none: they load as before, once, and the next autosave writes version 3 with the baseline of the level as it is then.
- On load (`restoreThings`): a plant the level changed or removed keeps no saved state and its waiting timers are dropped; so are the timers of a changed or removed person.
- People (`mergeNpcPopulation`): the population made from the level as it is now takes over the saved state (age, needs, place, memories, opinions, trade stock, the director's mode and hit points) of every person the level did not touch, by id. A changed or new person comes fresh; a removed person is not in the run. With no change to the people the old path is used unchanged. New in `src/sim/`: `NpcPopulation::adopt`, `NpcDirector::adopt`, `TradeMarket::restoreState(text, skip)`.
- Buildings: `buildings.json` version 2 adds `levelIds` (which building of the store is which building of the level). The sim's building store is not changed. `BuildingLayer::mergeLevel` removes the store buildings of removed and changed level buildings and places the changed and new ones from the level; what the clan built, and the level buildings it did not change, are left alone. A version 1 file keeps the links the level made at the start.
- The status line says "Loaded clan.json: day N. The level updated 2 things" when the level changed anything since the save.
- After an Editor save while a run is loaded (`runLoaded`), Play (F1) rebuilds the play state from the level and then loads the run again with the same merge, instead of starting the run over. Without a loaded run, F1 works as before.

## Technical choices (deviations from the Codex wording)
- The Codex says each of `things.json`, `buildings.json` and the placed people's save stores the baseline. One baseline for all six kinds lives in `things.json`: the files are written in the same autosave, so three copies could only disagree. `buildings.json` stores only the link its store needs (`levelIds`), because the store gave its own ids to the level's buildings. The people's save (`npcs.json`) is unchanged: its ids are the level's ids already. Saves changed: `things.json` 2 to 3, `buildings.json` 1 to 2, both with a migration; no change beyond the baseline and the link, so no question for the owner.
- A thing the level changed is compared with the file as the Editor wrote it, not with the run's own state: a person who walked away from their home is still "untouched" because the level entry is what is hashed.

## Tests (tests/game/level_merge_test.cpp, "US-305 ...")
Baseline (hash and text round trip, a damaged text is none), Baseline changes (moved, new, deleted, untouched), Edited and Untouched (a bush moved in the level is fresh, the others keep "picked"), Untouched with no edit, Timers (the moved plant's waiting timer is dropped, the other counts down), Removed (a person deleted: not in the run, the survivor keeps their age, the status line counts it), Changed person (starts fresh), Old save (a version 2 file loads as before and is written with a baseline), Round trip (save, load, save: the same baseline and state), Buildings (a moved hut stands in its new place, the clan's other building stays, links round trip), Play from the Editor (save, F1: the run is back with the edit merged).

## Manual checks (docs/evidence/US-305/)

2. Run the game on a hand-made level with `--load`, move a berry bush in the Editor, save, press F1: the bush stands in its new place with berries, the other bushes keep what was picked, and the status line says "The level updated 1 thing".
