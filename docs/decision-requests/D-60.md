# D-60 M11 design decisions (K-M11)

Status: **Decided by Dominus (delegated)**, 2026-10-06, under D-41 (the owner delegates the design questions of M10-M14 to Dominus). The owner may override any line later; if one changes, the story that built it is reopened. Design document: docs/plans/M11-data-editors-design.md.

| Q | Question | Options considered (recommended first) | Decision and reason |
|---|---|---|---|
| Q1 | How many schemas | One per file shape with `index.json` mapping globs; one per file (185 near-identical files for interactions and NPC kinds); one big schema | **One per file shape plus `assets/data/schemas/index.json`.** 66 interaction files share one shape; one schema each would be 66 copies to keep in step. The brief's "one schema per data file" is met for every single file and every family has one schema. |
| Q2 | How much JSON Schema | The brief's subset plus `required`, `additionalProperties`, `minItems`, `maxItems`, `maxLength`, `example`, `format`, `provides`; the bare subset; full JSON Schema through a library | **Brief subset plus those few keys.** Maps keyed by id (quest steps, `sim` sections) and the catalogs a file provides cannot be said otherwise; a library would add a dependency and an ADR for a form builder that needs ten keys. |
| Q3 | When a loaded value is wrong | Fatal for type, range, enum and required, warning for unknown fields and dangling refs; everything fatal; everything a warning | **Fatal for the first group, warning for the second at load; both errors in CI and in the Editor.** The loaders already refuse bad ranges; an unknown key may be a deliberate note. CI is where a typo must fail. |
| Q4 | Line numbers in errors | A scanner mapping JSON paths to lines; search the source text for the key (as quests do); no line | **Scanner (`JsonLines`).** Searching for a key finds the wrong line when the key repeats (`damage`). |
| Q5 | How the Data tab writes a file | House-style canonical writer on ordered JSON with the leading comment block kept; patching the text in place; always pretty-print everything | **Revised at US-191: patch the text in place** (it was "canonical writer" at K-M11). The canonical writer would have reformatted files on their first save and lost every comment inside a file; the patcher keeps every unchanged byte, so a one-value change is a one-line diff, and its tests over all 183 shipped files proved it can add and remove list entries and members safely. |
| Q6 | Undo in the Data tab | Own snapshot stack per open file; join the Level `History` | **Own stack** (up to 200 snapshots). The Level `History` holds Level commands; a data edit is not one, and mixing would let Ctrl+Z in the map undo a form. |
| Q7 | Live reload of catalogs and mechanics | Ids everywhere, catalog and mechanics sets live, tiles and materials stay at next start; keep pointers and reload at next start; restart the run on save | **Ids and live sets** (design section 7). It is what CI-007 asked and what the exit criterion says; tiles and materials are held as numbers in the map, so they stay next-start and the form says so. |
| Q8 | What rename touches | Schema `ref` fields, levels, rule-language strings and directive lines of `.dlg`, by whole identifier; also prose | **Everything with a rule meaning, nothing in prose.** Rewriting prose would damage dialogue. |
| Q9 | Where the Quick check runs | In process, time-sliced on the game thread; a child process of `odysseus_headless`; a worker thread | **In process, time-sliced.** The Platform layer owns processes and threads (ADR-007 single thread); 30 days a tick keeps the screen alive and is deterministic. |
| Q10 | Name and place of the Game Rules code | `sim/play_rules` | **`play_rules`**, because `game_rules.*` is the M7 rule-language host. Rules are read by the Simulation, so the headless run honours the switches. |
| Q11 | Where profession routines live | `day` and `night` on each profession in `hero/professions.json` (US-290 format); a new file per role; `routines.json` as the brief says | **On the professions**, in the US-290 format, with the new `prefer` weights on blocks. The Codex (v2.11) forbids a second format and `routines.json`. |
| Q12 | How the Cut tool rebuilds the atlas | Library call to the existing atlas code if one exists, else run the tool; always run the tool | **Library call** (decided at US-192 after reading `apps/atlas`): the functions the cutter uses already live in the game library (`loadCuts`, `cutAtlas`, `saveAtlas`, `loadContentCuts`, `cutContent`, `saveContent`), so `rebuildAtlases` in `src/game/atlas_cuts.cpp` calls them; no child process. The Cut tool writes `cuts.json` (characters, tiles) and `content-cuts.json` (the frames the data fields name); the running game reads the new atlas at its next start. |
| Q13 | Gate check of K-M11 step 1 | M10b walkthrough was deferred by the owner on 2026-10-06 (commit f1eeb9e) and `main` carries M10b | **Proceed.** X-M10b ran its full verification and CI; only the owner's walkthrough answer is open and that is his to give any time; it blocks nothing in M11. |
| Q14 | What a rename does while the open file has unsaved changes (US-193) | Refuse until the owner saves or undoes; write the open file's edits too; ask | **Refuse with the reason.** A rename writes files, the open one included; writing the owner's unsaved edits as a side effect would be a surprise. A delete is an edit of the open file and needs no such rule. Saved runs are not rewritten (a run save is the player's, not data). |
| Q15 | What the Quick check reads and how long it runs (US-194) | The saved files on disk, 20 years; the open document; a shorter run | **The saved files, 20 years on the seed of the level in play**, 30 days per update; unsaved edits are named in the status line. The headless program keeps its own loop (it prints more); both use the same `World` and report. |
| Q16 | Mechanics data live (US-194, left over from Q7) | Swap by value between ticks, refusing what the clan cannot take; restart the clan; leave at next start | **Swap between ticks, refuse what cannot change** (ticks per day, days per season, the top of the needs scale, a hero file that drops the preset or comfort in play); the old rules stay and the reason is said. |
| Q17 | Where the Game Rules switches are read and how presets move (US-195) | A flag test where each system starts or is drawn; thread a switch through every constructor; one comfort section next to `newGame`; keep hero.json as it was | **A flag test at each system's doorway, no separate `comfort` section** (the comforts are `newGame.comforts`), and the moved keys leave `hero.json` while the loader still reads them for what a rules file leaves out, with a warning, for one version. A set of rules lays over `standard.json`, so a file names only what it changes. A run keeps the rules it began with (in its save, version 2); a level may name `rules` (level version 7). |
| Q18 | What a routine's weights multiply, and who has a profession (US-196) | The tags an interaction file would carry (a new field in 60 files); the id, the tags it asks of its target and the target's tags; store a profession on every clan member | **The id, the tags the interaction asks of its target and the target's own tags**, each counted once; a clan member's profession is worked out from their skills (hunter when hunting is above gathering, else gatherer); in the clan the tags are the action words and `work`. Needs win: the interruption rule for placed persons, `routineDangerBelow` for the clan. The timeline lives in the Editor's schedule form and in the Data tab and never writes by itself. |
