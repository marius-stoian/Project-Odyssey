Anima Prompt Catalog

Living catalog kept by Anima (the anima skill and Dominus's Anima hat). IDs are never reused; a revised prompt keeps its ID with a dated note. Placeholders are written in double braces. Last updated 2026-10-01 (Project Odyssey Codex v2.4).

Style Profile

  • Concise; prefers tables and diagrams over prose.
  • Business Analyst background (BABOK, BPMN, BRDs); treats one formal requirements document as the source of truth and keeps IDs stable.
  • Wants deliverables as Word and Excel files saved in Google Drive, mirrored into the repository.
  • Gives feedback as [square-bracket] comments inside documents, resolved in one pass.
  • Names personas and teams: Dominus (all hats), Mraw / Dominus Avengers (full team), Anima (prompts); builds with the Amek workflow (Brief, Codex, Assemble).
  • Prefers XML-tagged prompts for autonomous agents (2026-09-29).
  • Takes design and scope decisions himself in short question rounds: up to four questions, two to four options each, the recommended option first, short context; often answers in free text that narrows or widens scope, which is recorded word for word (2026-09-30).
  • Wants decisions one by one when there are several, each with succinct context (2026-10-01).
  • Wants assembly to run with little of his time, then reviews delegated decisions afterwards; switches between "owner decides" and "Dominus decides" per milestone range (2026-10-01).
  • Never wants AI vendor or model names, or co-author lines, in project files, commits or pull requests.

Best Practices (v2026-09-29)

Canonical list: section 8 of the Anima skill. Highlights: clear and direct, with success criteria; explain why; positive, calm wording; XML sections; long inputs first; examples in example tags; say exactly what done means; explicit stop conditions for autonomous work; state files for multi-session work; test every prompt with two or three inputs including an edge case.

Lessons from Project Odyssey (2026-10-01): generate repeated story prompts from one data source shared with the requirements document, so acceptance criteria match word for word; check every generated replacement lands in the intended prompt (CI-009 came from a replacement that hit the first match); give every rule its scope ("from M8b", "for M10-M14") so exceptions stay readable.

ANM-003 Mraw build loop L-01

Use: the standard procedure for every unit of work in a Codex. Source: Anima, Project Odyssey Codex v1.1, revised to v2.4. Date: 2026-09-29, revised 2026-10-01. Tags: codex, build-loop, tdd, acceptance.

<prompt id="L-01" codex="{{CODEX_VERSION}}" name="Mraw build loop">
<instructions>
1. Readiness: every owner decision in <dependencies> is Decided in docs/decisions.md and every prerequisite is Done; an undecided design question goes to {{OWNER_OR_DOMINUS}} as the Charter says.
2. Branch (or continue a paused branch). 3. Plan (architect) into docs/plans/<ID>.md. 4. Tests first from the acceptance criteria (tester).
5. Content as data if needed (designer). 6. Implement until tests pass with zero warnings (programmer).
7. Verify with {{LOCAL_CHECK_COMMAND}} ({{WHICH_CONFIGURATION_LOCALLY}}); CI covers {{WHICH_CONFIGURATION_IN_CI}}.
8. Accept against evidence (acceptor); after {{MAX_REJECTIONS}} rejections: Failed + codex issue.
9. Docs and teach-back (writer). 10. CHANGELOG, commit, merge, push; Done when {{DONE_SIGNAL}}.
11. Resume point, progress snapshot and assembly report; continue, or end the session cleanly.
</instructions>
<stop_conditions>Blocked dependency; repeated rejection; codex issue; missing authentication.</stop_conditions>
<output_format>Assembly report.</output_format>
</prompt>

ANM-008 Dominus council and milestone planning

Use: the owner asks Dominus to council and plan a big new feature into milestones. Source: Dominus, Project Odyssey Rounds 13-17. Date: 2026-10-01. Tags: dominus, council, planning, requirements.

Dominus, council and plan {{FEATURE_GOAL}} as new milestones in the requirements and the tracker.
Steps the council follows:
1. Read the current state (requirements version, Codex version, status, latest progress snapshot, the code that the feature touches) before advising.
2. Ask the owner the questions that change the shape of the plan, in rounds of up to four (two to four options each, recommended first, one line of context each). Record free-text answers word for word; flag answers that reverse a cut-list item or move a kill gate.
3. Write the plan: milestones (IDs follow the project's insertion convention), epics, stories with three Gherkin scenarios each, requirement IDs, an ADR when the architecture changes, estimates, risks.
4. Update the requirements (new version, resolution-log round, dependency row) and the tracker from one data source; write the brief docs/plans/{{BRIEF}}.md for Anima.
5. Close with the council verdict, what each discipline found, where they collide, and the next step ("Anima, Codex vX.Y").

ANM-009 Owner decision round

Use: any time an agent needs a design or scope decision from the owner. Source: Dominus and Anima, Project Odyssey D-22. Date: 2026-10-01. Tags: decisions, owner, question-round.

Ask the owner in chat, one round at a time (up to four questions; when he asks for "one by one", one question per round).
Each question: one to three sentences of context, two to four options, the recommended option first and labelled "(Recommended)", each option with one sentence on its consequence.
After the round: record each answer in docs/decisions.md as "Decided (owner, {{DATE}})" with the owner's own words when he wrote free text; update the requirements first if the answer changes them; then continue.
