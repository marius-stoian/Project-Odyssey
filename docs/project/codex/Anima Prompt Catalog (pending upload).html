Anima Prompt Catalog

Living catalog kept by Anima (the anima skill and Dominus's Anima hat). IDs are never reused; a revised prompt keeps its ID with a dated note.

Style Profile

  • Concise; prefers tables and diagrams over prose.
  • Business Analyst background (BABOK, BPMN, BRDs); treats one formal requirements document as the source of truth.
  • Wants deliverables as Word and Excel files saved in Google Drive.
  • Gives feedback as [square-bracket] comments inside documents, to be resolved in one pass.
  • Names personas and teams: Dominus (all hats), Mraw / Dominus Avengers (full team), Anima (prompts); builds with the Amek workflow (Brief, Codex, Assemble).
  • Prefers XML-tagged prompts for autonomous agents (2026-09-29).

Best Practices (v2026-09-29)

Canonical list: section 8 of the Anima skill. Highlights: clear and direct, with success criteria; explain why; positive, calm wording; XML sections; long inputs first; examples in example tags; say exactly what done means; explicit stop conditions for autonomous work; state files for multi-session work; test every prompt with 2-3 inputs including an edge case.

<prompt id="L-01" codex="{{CODEX_VERSION}}" name="Mraw build loop">
<instructions>
1. Readiness: every owner decision in <dependencies> is Decided in docs/decisions.md and every prerequisite is Done in docs/status.md; otherwise write a decision request, mark Blocked, move on.
2. Branch. 3. Plan (architect) into docs/plans/<ID>.md. 4. Tests first from the acceptance criteria (tester).
5. Content as data if needed (designer). 6. Implement until tests pass with zero warnings (programmer).
7. Verify: full builds and all tests (tester). 8. Accept against evidence (acceptor); after {{MAX_REJECTIONS}} rejections: Failed + codex issue.
9. Docs and teach-back (writer). 10. Commit, merge, push; status Done. 11. Assembly report; continue, or end the session cleanly.
</instructions>
<stop_conditions>Blocked dependency; repeated rejection; codex issue; missing authentication.</stop_conditions>
